## Why PR #3 was closed: a bug in backtest_gate.py's slot fallback

PR #3 touched only `hypotheses/backlog.md` and `notes/2026-09-17.md` — no
challenger config, no strategy code. The gate rejected it anyway, with no
reason more specific than "Gate failed" in the PR comment. Reproduced it
locally: `gate/backtest_gate.py:changed_slot()` looks for a changed
`configs/challenger*.yaml` in the diff, and when it finds none (true for any
notes-only PR) it falls back to `config.challengers()[0]`, which is always
`challenger1`, and re-runs *that* slot's backtest over the full
`backtest_gate.max_days` (365) window regardless of whether the PR touched
it. Confirmed by running `python gate/backtest_gate.py` on a clean checkout
with zero diff against origin/main:

```
backtesting configs/challenger1.yaml (H1)
...
cost coverage -1.31 below 1.0
gross pnl -1773.85 is not positive even before costs
max drawdown -45.02% worse than -30%
5 fills in one pair in one day exceeds 4
```

challenger1 is running H1 (mean_reversion, 240h window), approved and
already 2.7 days into its prospective 60 day test. It doesn't need to
re-pass `backtest_gate` — that gate is for a *new* hypothesis entering a
slot — but the fallback logic backtests it anyway on every PR that doesn't
touch a challenger config, and it now fails badly on the full 365 day replay
(see below), so it fails the whole PR.

**Consequence: right now, any PR that does not modify a `configs/
challenger<k>.yaml` will be auto-rejected**, including a plain notes-only
"no bug found" PR on a busy-slot day, for as long as challenger1's backtest
keeps failing this bound — i.e. for the rest of H1's 60 day window unless
the trailing-365-day window rolls past enough of the crash to change the
number, which is not guaranteed. This is a bug in protected code
(`gate/backtest_gate.py`) I cannot fix; flagging for Fin. Two independent
ways to fix it that don't touch the plausibility bar itself: (a) skip
`backtest_gate` entirely when the diff touches no challenger config and no
strategy code (mirroring what `check_ledger.py` already does), or (b) don't
fall back to slot 1 — skip the gate when no slot changed. Either would have
let PR #3, and would let today's notes-only PR, merge on their own merits.

This PR will likely hit the exact same wall for the same reason. I'm
submitting it anyway so the record is complete and readable via `gh pr
view` even if closed, same as #3.

## Whether a different mechanism can clear the crash-year backtest

#3 already established that filtered/regime-gated/concentrated momentum and
a cross-sectional ranker all lose badly over the real trailing 365 days
(every pair down 46-81% peak to trough; see notes/2026-09-17.md for the
per-pair numbers, unchanged in kind today). That only covered the momentum
family. I tried the other running family: mean reversion, with a
structurally different risk control — a hard stop-loss expressed in the
same z-score units as the entry, rather than mean_reversion's current
signal-only exit (hold until z recovers to -exit_z, however long that
takes). Added a prototype `mean_reversion_stop` to bot/strategy.py locally
(not committed): same entry as H1 (z < -entry_z), but exit early if z falls
below -(entry_z + stop_extra_z) — i.e. cut the trade if the dislocation
keeps widening instead of reverting, rather than riding it down indefinitely
like H1 does.

Backtested over the same 365 day window (10 pairs, live cost model):

| params (window_hours/entry_z/exit_z/stop_extra_z) | total return | max DD | gross pnl | cost coverage | n_trades | max fills/pair/day |
|---|---|---|---|---|---|---|
| H1 as running (240/2.0/0.5, no stop) | -31.2% | -45.0% | -1773.85 | -1.31 | 879 | 5 |
| 240/2.0/0.5/2.0 (loose stop) | -30.8% | -44.3% | -1548.46 | -1.01 | 991 | 10 |
| 240/3.5/1.0/1.0 (rare entry, tight stop) | -14.7% | -20.0% | -1015.46 | -2.24 | 189 | 7 |

The tight-stop, rare-entry version cuts the drawdown a lot (-45% to -20%)
and trades far less, but gross pnl stays negative in every version — the
stop limits how much a losing trade costs, it does not make the average
trade a winner. Buying a 2-3.5 sigma dip against a 240h mean and holding for
reversion lost money on average in this specific window regardless of how
tightly the losers were cut, because the mean itself was falling with the
price: a dip that looks 2 sigma extreme today is unremarkable a week later
once the rolling mean has caught down to it, so the position sits through
the fall waiting for a reversion that the trend keeps postponing. A wider
grid (I started a 54 combination sweep across window/entry_z/exit_z/
stop_extra_z; it did not finish in the run — pandas rolling recompute per
bar makes each backtest slow, ~1-2 minutes, and 54 of them did not fit in
this session) is unlikely to change the conclusion given the pattern across
the three points above: tightening the stop trades drawdown for coverage,
it doesn't flip the sign of gross pnl.

Combined with #3's momentum-family results, that's two independent families
(trend following and mean reversion) plus a cross-sectional selection
overlay, none of which show positive raw edge over this specific trailing
year. I did not add mean_reversion_stop to bot/strategy.py or open a slot
for it — a hypothesis with a backtest this bad shouldn't be submitted just
to have something to submit, and it fails backtest_gate's own bounds on its
merits regardless of the slot-1 bug above.

## What I'd want a future run to try instead

Not "tune mean reversion harder" — three parameter points here plus #3's
grid on the momentum side both point the same way: the losing mechanism is
directional (long-only positions can't avoid a one-way fall), not a sizing
or exit-timing detail. A hypothesis that has a real shot needs either (a) a
reason to expect the *next* 60-90 days specifically to differ from the
trailing year (this system only judges prospectively, so a backtest-only
argument doesn't help get past the gate anyway), or (b) a mechanism that is
flat by construction during a sustained one-directional move and only
engages on a specific, rarer pattern than "N sigma below a moving mean" —
something that has a real reason to be right more often than a dip buy in a
falling market, not just a tighter trigger on the same dip-buying logic.
